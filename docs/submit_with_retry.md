# `src/submit_with_retry.ts` — отправка с ретраями

`submitBundleWithRetry(...)` повторяет отправку до `maxRetries` раз. С каждой попыткой чаевые
растут, для tip-транзакции может браться свежий blockhash, а при `regionFallback` расширяется
набор регионов. Между попытками пауза 2 с.

Чаевые на попытке `n` (с 0): `round(calcTipFn(strategy) × (1 + n × tipIncreasePercent / 100))`.
При 20 %: 1.0M → 1.2M → 1.4M (рост линейный, не сложный процент).

## Что изменено относительно ТЗ и почему

Формулы и порядок шагов — ровно как в ТЗ. Дополнено то, чего в ТЗ не было:

### 1. `regionFallback` — поведение придумано мной, проверьте
В ТЗ поле есть, а поведения нет. Сделано так: попытка 1 — регионы как переданы; **со второй
попытки все регионы включаются** (`enabled: true`, в том числе `tokyo`/`ny`). Исходный массив не
мутируется. Если вы имели в виду другое (например, перебор регионов по одному) — скажите.

### 2. `maxRetries` — это общее число попыток
По ТЗ цикл `0..maxRetries-1`, то есть `maxRetries: 3` = 3 попытки всего, а не 1 + 3 повтора.
Так и сделано, отмечено в комментарии к полю. `maxRetries < 1` → ошибка до отправки.

### 3. Округление чаевых
`tip × 1.25` может быть дробным, а лампорты — целые (и `submitBundleMultiRegion` дробные
отклоняет). Поэтому `Math.round`.

### 4. Ошибка `calcTipFn` считается неудачной попыткой
Например, упал внешний источник чаевых: это ретраится так же, как ошибка отправки.

### 5. Нет паузы после последней попытки
Чтобы ошибка «все упали» прилетала сразу, а не через лишние 2 с.

### 6. Итоговая ошибка содержит причину
`throw new Error('Бандл не отправлен за N попыток', { cause: lastError })` — последняя ошибка
доступна в `err.cause`.

### 7. Импорты с `.js`
Импорты типов оставлены как в ТЗ (`./jito_regions.js` и т.д.). TypeScript и vitest
сопоставляют их с `.ts`-файлами, сборка проходит. Остальные файлы проекта импортируют без
расширения — при переходе на настоящий ESM (`"type": "module"`) их нужно будет привести к `.js`.

## Как встроить в код

```ts
import { submitBundleMultiRegion, DEFAULT_JITO_REGIONS } from './jito_regions';
import { calculateTip, getRecentLandedTips, JITO_TIP_FLOOR_HOST } from './tip_strategy';
import { submitBundleWithRetry } from './submit_with_retry';

const recentTips = await getRecentLandedTips(JITO_TIP_FLOOR_HOST).catch(() => []);

const result = await submitBundleWithRetry(
  signedTxs,
  DEFAULT_JITO_REGIONS,
  { type: 'percentile', percentile: 75, minLamports: 10_000 },
  { maxRetries: 3, tipIncreasePercent: 25, blockhashRefresh: true, regionFallback: true },
  watcher,                                   // уже запущенный BlockhashWatcher
  tipPayer,
  blockhashOfSignedTxs,
  submitBundleMultiRegion,                   // реальная отправка
  (s) => calculateTip(s, recentTips),        // ← обязательно обёртка
  log,
);
```

### ⚠️ Главное ограничение: `blockhashRefresh` не спасает истёкшие транзакции
Свежий blockhash получает **только tip-транзакция**. Ваши транзакции уже подписаны со своим
blockhash, и ретрай их не пересобирает. Blockhash живёт ~150 слотов (≈60–90 с). Если ваши
транзакции истекли, все повторы будут отклонены, сколько бы ни росли чаевые.

Практические выводы:
- Держите `maxRetries` небольшим (2–3). Худший случай при 3: 3 × 30 с + 2 × 2 с ≈ 94 с.
- Подписывайте транзакции **свежим** blockhash из watcher непосредственно перед отправкой.
- **Лучшее решение (следующий шаг):** передавать вместо готовых транзакций функцию-сборщик
  `buildTransactions(blockhash) => Promise<VersionedTransaction[]>` и на каждой попытке
  пересобирать и переподписывать всё под свежий blockhash. Это меняет контракт, поэтому не
  сделано без вашего согласия.

### Безопасность повторов
Повтор не приводит к двойному исполнению: если бандл на самом деле приземлился, а мы
посчитали попытку неудачной (например, по таймауту), повторная отправка тех же подписанных
транзакций будет отклонена как дубликат. Tip-транзакция исполняется только внутри своего
бандла, поэтому лишних чаевых тоже не будет.
