# `src/jito_regions.ts` — отправка в несколько регионов

`submitBundleMultiRegion(transactions, regions, { tipPayer, tipLamports, recentBlockhash }, log)`
параллельно шлёт бандл во все регионы с `enabled: true` и возвращает
`{ bundleId, region, tipAccount }` региона, который **первым принял** бандл.

## Что изменено относительно ТЗ и почему

### 1. `getTipAccounts` — POST, а не GET
В ТЗ: `GET https://{url}/api/v1/getTipAccounts`. У Jito это JSON-RPC-метод: путь тот же, но
запрос — `POST` с телом `{"jsonrpc":"2.0","id":1,"method":"getTipAccounts","params":[]}`.
Обычный GET на этом пути не работает. Путь оставлен как в ТЗ, поменян только метод.

### 2. `Promise.any` внутри `Promise.race`, а не голый `Promise.race`
`Promise.race` завершается на **первом событии, включая ошибку**: если ближайший регион
быстро ответит 429, вся отправка упадёт, хотя другие регионы приняли бы бандл. Это противоречит
пункту ТЗ «ошибки отдельных регионов не останавливают остальные». Поэтому:
- `Promise.any` — ждёт первого **успешного** региона;
- `Promise.race([Promise.any(...), таймаут])` — общий дедлайн 30 с.

### 3. Проигравшие регионы не отменяются
После победы одного региона запросы в остальные продолжают идти. Лишние копии бандла только
повышают шанс попасть в блок. Двойной оплаты не будет: пользовательские транзакции во всех
копиях одинаковые, а бандл атомарен, поэтому приземлится максимум один.

### 4. Вынесена валидация в `bundle_validation.ts`
Чтобы новый модуль не тянул gRPC-клиент `jito-ts` (тяжёлый, и он не нужен для HTTP-отправки),
проверки бандла вынесены в общий файл. См. [bundle_validation.md](bundle_validation.md).

### 5. Сверх ТЗ
- Проверка входа до сети: 1–4 транзакции, все подписаны, чаевые ≥ 1000 лампортов.
- Пустой список включённых регионов → сразу ошибка, без запросов.
- По таймауту все незавершённые запросы прерываются через `AbortController`.
- Для каждого региона свой случайный tip-аккаунт (как и запрашивалось).

## Как встроить в код

```ts
import { DEFAULT_JITO_REGIONS, submitBundleMultiRegion } from './jito_regions';

const result = await submitBundleMultiRegion(
  signedTxs,                       // 1–4 подписанные VersionedTransaction
  DEFAULT_JITO_REGIONS,            // или свой список
  { tipPayer, tipLamports: 50_000, recentBlockhash },
  (level, msg) => logger[level === 'success' ? 'info' : level](msg),
);
console.log(result.bundleId, result.region);
```

- **Как правило, напрямую не вызывайте** — передавайте как `submitFn` в
  `submitBundleWithRetry`; сигнатуры совместимы.
- **Регионы:** включайте ближайшие к серверу. Из Европы — `amsterdam` и `frankfurt`, из США —
  `ny`. Лишние далёкие регионы почти не помогают, но тратят rate-limit.
- **Rate-limit Jito:** без авторизации — порядка 1 запроса в секунду на IP на регион. Каждая
  отправка — 2 запроса на регион (`getTipAccounts` + `sendBundle`). Если отправляете часто,
  стоит кешировать tip-аккаунты (они меняются редко) — это следующий шаг оптимизации.
- **`recentBlockhash`** берите тот же, что у ваших транзакций, или свежий из `BlockhashWatcher`.
- `bundleId` — это «бандл принят», а не «бандл в блоке». Приземление проверяйте отдельно
  (`getBundleStatuses` / подпись транзакции через RPC).
